# Перевірка якості аналізу

Тут зібрані CV з відомими проблемами і те, що аналіз мусить на них помітити.

- `cases/` вигадані приклади, вони є в репозиторії.
- `private/` справжні CV. Ця папка не потрапляє в git: CV містять персональні дані.

Як працювати з пропуском, який знайшов юзер:
1. Додай CV у `private/` і JSON-кейс поруч (формат як у `cases/example_student.json`):
   `line_contains` це шматок рядка, `verdicts` це які вердикти вважаються правильними.
2. Запусти `python evals/run_evals.py` і переконайся, що новий кейс падає.
3. Зміни рубрику (`cvmax/rubrics/`) або промпт (`cvmax/prompts.py`).
4. Запусти знову: новий кейс має пройти, а старі не впасти.

Модель відповідає не завжди однаково, тому перед тим як вважати зміну вдалою, проганяй кілька разів:
`python evals/run_evals.py --runs 3`. Наприкінці буде таблиця, яка перевірка скільки разів пройшла
(`!!` позначає нестабільні). Кожен прогін витрачає один запит до моделі на кейс, а безплатний Gemini
дає близько 20 запитів на день на модель, тому 3 прогони по 4 кейси це вже 12 запитів.

Порівняти моделі: той самий набір на Claude.
```
GEMINI_API_KEY=... python evals/run_evals.py --runs 3
CVMAX_PROVIDER=claude ANTHROPIC_API_KEY=... python evals/run_evals.py --runs 3
```
Дивись на рядок «Разом» і на нестабільні перевірки. Якщо Claude стабільно краще на тих самих кейсах,
є сенс перемикати основну модель (`CVMAX_PROVIDER` у Secrets).

Поля перевірки (`expect`):
- `line_contains`: шматки тексту рядка, про який перевірка.
- `verdicts`: які вердикти вважаються правильними (`keep`, `cut`, `shorten`, `rewrite`, `move`).
  `keep` означає «не чіпати»: перевірка падає, якщо рядок отримав інший вердикт або правку.
  `any` означає, що вердикт неважливий, а перевіряються лише заборонені слова нижче.
- `after_must_not_contain`: слова, яких не має бути в правці цього рядка. Так ловимо випадки,
  коли модель приписує людині діяльність, якої не було (напр. «analysed industries» замість «запрошував спікерів»).
- `type`: вид перевірки. Без нього це перевірка рядка (поля вище). Є ще два види, для вад над усім CV:
  - `"length"` з `min_cut_words`: правки разом скорочують CV щонайменше на стільки слів (рахуються лише правки,
    де `after` коротший за `before`). Так ловимо `over_length`.
  - `"mentions"` з `any_of`: хоч одне слово є в `edits[].after`, `edits[].section`, `missing_info` або `summary`.
    Так ловимо відсутній контакт (напр. `email`).

Кожен кейс автоматично отримує ще одну перевірку, `_no_invented_numbers` (вада `hallucination`): жодна правка
не вводить число, якого немає в CV, у `background` профілю чи в цитаті `before`. Числа в [дужках] дозволені.
Додавати її в `expect` не треба.

## Синтетичні кейси

Окрім справжніх CV є вигадані, у яких вади закладено навмисно. Вони лежать у `evals/synth/` (пари
`<програма>_s<seed>_<n>.json` + `.txt`, формат як у `cases/`, плюс `"synthetic": true` і поле `flaw` у кожному `expect`).
У типовий прогін вони не входять. Каталог вад, тобто як закласти кожну і які вердикти правильні, це `evals/flaws.json`.
- Прогнати: `python evals/run_evals.py evals/synth --runs 1`. Наприкінці буде таблиця «за вадами» (`By flaw`):
  скільки разів пройшла кожна вада, найгірші зверху. У `--json` вона лежить в `by_flaw`:
  `{"<вада>": {"passed", "total"}}`. `strong_keep` це контроль хибних спрацювань: рядки, які не можна чіпати.
- Нові кейси пише важка модель: `python evals/generate_synthetic.py --program all --n 2 --seed 7` (потрібен ключ).
  Кожен кейс проходить `validate_case`: фрагменти рядків є в тексті рівно раз, 300-1200 слів, без реальних компаній,
  контакти з `-example`. Наявні файли без `--force` не перезаписуються.
- Базова лінія для воріт окрема: `evals/synth_baseline.json`.

Сира модель проти повного шляху: за замовчуванням кейс іде так само, як у застосунку (`analyze_full`: детерміновані
перевірки, верифікатор правок, стабільний бал). З `--raw` йде лише `analyze_cv` без перевірок і верифікатора,
тобто те, що каже сама модель. Прожени обидва і порівняй таблицю «за вадами»: різниця показує, що додають ці шари.

## Ворота для автонавчання

Скрипт навчання (`scripts/learn.py`) зливає нові уроки лише якщо evals не стали гіршими.
- `--json PATH` пише результат прогону: `{"model", "runs", "passed", "total", "pass_rate", "cases": {"<кейс>/<перевірка>": {"passed", "runs"}}}`.
- `--baseline PATH` порівнює `pass_rate` з базовою лінією (`evals/baseline.json`). Код виходу 0, якщо
  `pass_rate >= baseline - 0.05` (допуск на шум моделі), і 3, якщо гірше. Порожня базова лінія (`total` = 0) не блокує.
- `--update-baseline` записує `evals/baseline.json` за цим прогоном (шлях можна задати через `--baseline`).
Один раз задай базову лінію з реальним ключем: `python evals/run_evals.py --runs 2 --update-baseline`.
Для синтетичних кейсів те саме з їхньою базовою лінією:
`python evals/run_evals.py evals/synth --runs 1 --baseline evals/synth_baseline.json --update-baseline`.
